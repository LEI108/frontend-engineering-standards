# 规范与 Skill 条件引用向导

> 版本：1.0.0  
> 本文只负责导航和条件触发，不替代正式规范或 Skill 正文。

## 1. 每次任务的读取顺序

1. 用户当前请求、已确认决策和授权范围；
2. 目标项目及适用子目录的 `AGENTS.md`；
3. 项目业务、接口、设计、安全和发布合同；
4. `standards/前端工程开发规范（通用版）.md`；
5. AI 参与时读取 `standards/AI前端协作与分层验证规范.md`；
6. 匹配的技术栈 Profile 和已填写的项目技术基线；
7. 按本向导选择 Skill；
8. 任务模板、历史变更记录和外部参考。

Skill 是执行工作流，不是更高优先级的规范。提示词是启动入口，不是隐式修改、commit 或部署授权。

## 2. Skill 使用方式

### 2.1 已安装模式

用 `scripts/install-skills.ps1` 将团队副本安装到 Codex 的 skills 目录后，可以按名称触发，例如：

```text
使用 $precision-frontend-engineering 分析并实施这个现有页面修改。
```

只有当前客户端已发现该 Skill 时，名称触发才可靠。更新团队副本后，需要重新安装或同步个人副本。

### 2.2 显式读取模式

未安装或使用其他 AI 工具时，明确要求读取包内入口：

```text
先完整读取 正式前端开发规范/skills/lean-code-edits/SKILL.md，
再按其中引用条件读取所需 reference。
```

不得声称“已加载 Skill”却没有读取入口文件。Skill 引用的相对路径以该 Skill 目录为基准。

## 3. 任务路由

| 任务类型 | 默认规范 | Skill 组合 |
| --- | --- | --- |
| 琐碎修复、局部维护 | 通用总纲 | `lean-code-edits` |
| 现有应用的非平凡功能、API、状态或复用调整 | 通用总纲 + 对应 Profile | `precision-frontend-engineering` + `lean-code-edits` |
| 新页面、设计系统、视觉提升或响应式体验 | 通用总纲 + 对应 Profile | `frontend-design`；现有仓库再加 `precision-frontend-engineering` |
| Lanhu 设计实现 | 通用总纲 + AI 协作规范 + 对应 Profile | `lanhu-design-build` + `frontend-design`；现有仓库通常再加 `precision-frontend-engineering` |
| 图表普通业务页面 | 通用总纲 | `lanhu-design-build` 的 `chart-runtime.md` 仅在有 Lanhu/设计证据任务时使用；否则用项目图表规范 |
| 数据驾驶舱/展示墙 | 通用总纲 + 项目缩放合同 | `lanhu-design-build` 的 dashboard 分支，仅在定义匹配时加载 |
| 组件抽取/共享能力 | 通用总纲 | `precision-frontend-engineering` + `frontend-design` 的组件边界 reference |
| 接口、Mock、上传下载、预览 | 通用总纲 + 接口合同 | `precision-frontend-engineering` |
| CSS 命中、Teleport、运行样式问题 | 通用总纲 + Profile | `precision-frontend-engineering`；涉及 Lanhu 证据再加 `lanhu-design-build` |
| Git 提交 | Git 提交与 AI 溯源规范 | 通常无需 Skill |

只加载完成任务所需的最小组合，不把四份 Skill 每次全部塞入上下文。

## 4. 四份 Skill 的职责

### 4.1 lean-code-edits

负责日常执行姿态：只暴露实质不确定性、最小实现、精准改动和任务级验证。适合所有普通修改作为基础护栏，但不替代复杂前端合同和视觉流程。

### 4.2 precision-frontend-engineering

负责现有应用中的证据化前端工程：工作区保护、调用链、API/Mock 合同、组件边界、精确修改、运行选择器和分层交接。非平凡的现有项目修改优先加载。

### 4.3 frontend-design

负责视觉方向、产品适配、设计系统、响应式、可访问性、性能和前端界面质量。现有产品必须保持既有设计语言；只有绿地或明确重设计任务才建立新视觉方向。

### 4.4 lanhu-design-build

负责 Lanhu 证据链、设计版本锁、MasterJSON、属性来源、资源、首轮运行门和视觉/交互验收。只有 Lanhu 或相同证据强度的设计实现任务才加载完整工作流。

## 5. 重叠规则如何裁决

- `lean-code-edits` 与 `precision-frontend-engineering`：前者是基础行为，后者为非平凡现有前端任务补充具体合同和验证。
- `frontend-design` 与 `precision-frontend-engineering`：前者决定产品/视觉质量，后者保护现有代码和数据边界；现有项目两者并用时先尊重现状和用户明确的设计授权。
- `lanhu-design-build` 与 `frontend-design`：Lanhu Skill 决定设计事实和证据门，frontend-design 补充一般 UI 工程判断；不能用审美偏好覆盖已锁定设计证据。
- Skill 与正式规范：正式规范优先。Skill 发现冲突时报告，不静默选择。
- Skill 与实时工具 Schema：对于工具参数和能力，以实时 Schema 为事实；若与 Skill 不兼容，停止相关调用并报告版本漂移。

## 6. 条件 reference

Skill 入口会说明何时读取 reference。必须完整读取已选中的 reference，但不要为简单任务预加载所有资料。

常见路由：

- API、Mock、文件合同：`precision-frontend-engineering/references/api-contracts-and-mocks.md`；
- 组件复用：`precision-frontend-engineering/references/component-reuse-and-boundaries.md`；
- CSS 与验证：`precision-frontend-engineering/references/focused-verification.md`；
- Vue 视觉实现：`frontend-design/references/vue.md`、`accessibility.md` 和按需工程 reference；
- Lanhu：任何工具调用前读 `lanhu-evidence.md`，改代码前读 `code-quality.md`，改前和交付前读 `acceptance.md`。

## 7. Skill 不可用或外部依赖失败

1. 明确说明没有成功加载的 Skill、reference 或工具；
2. 退回正式规范和项目合同；
3. 将依赖该能力的验证标记为未完成或阻断；
4. 不发明设计值、接口字段、工具结果、运行结论或视觉结论；
5. 外部工具恢复后从锁定事实和版本继续，不混用旧缓存。
