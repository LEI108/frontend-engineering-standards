# 前端工程开发规范（通用版）

> 版本：1.0.0  
> 性质：框架中立的正式总纲  
> 适用范围：新建、维护、迁移和评审 Web 前端项目

## 1. 规范用词与目标

- **必须（MUST）**：不满足时不得声称符合本规范；进入提交或发布前必须修复或登记经批准的例外。
- **应该（SHOULD）**：默认执行；偏离时应有具体原因和验证证据。
- **可以（MAY）**：由项目基线或任务上下文决定。

本规范的目标是让代码具备正确性、可理解性、可维护性、可验证性、可访问性、安全性和可追溯性。它不规定某个框架、目录名、路由模式、接口包裹或视觉主题；这些内容由 Profile 和项目技术基线确定。

## 2. 开发边界与事实来源

1. 修改前必须识别当前阶段：分析、方案、实现、静态验证、运行验证、视觉验收或交接。
2. 只读授权不等于写入授权；实现授权不自动包含 commit、push、部署、数据库或外部系统操作。
3. 接手现有项目时，必须先检查适用指令、工作区差异、目标调用链和项目自己的验证命令。
4. 用户或同事已有修改视为受保护资产。不得擅自回滚、覆盖、格式化或夹带整理。
5. 业务、接口、权限、设计和运行结论应标记为已确认、暂定、待确认、冲突或风险，不把推测写成事实。
6. 需求歧义会改变用户可见行为、数据、权限或公共合同时，必须先确认；无实质影响时采用最窄、最符合现状的假设继续。

## 3. 需求、范围与变更设计

非平凡变更至少建立一份简短变更地图：

```text
目标和验收：
明确不做：
受影响路由/模块：
现有行为和必须保留项：
接口、数据和权限合同：
修改文件与语义锚点：
风险和回滚：
最小验证：
未验证项：
```

- 每一处改动应能追溯到需求、必要的兼容处理或本次改动产生的孤儿清理。
- 不顺手重构邻近代码，不为假设中的未来需求增加抽象、配置或依赖。
- 新增依赖、公共 API、持久化结构、权限、外部接口或发布行为属于范围变化，应重新评估和确认。
- 复杂任务拆成可评审、可验证、可回滚的小批次；不要把功能、格式化、无关修复和架构重构混成一批。

## 4. 架构与所有权

### 4.1 按变化原因组织

代码优先围绕业务领域、功能或稳定技术职责组织。目录名称不是目的，清晰的所有权才是目的。

- 页面/路由层负责页面编排、导航输入和页面级状态。
- 业务组件负责可命名的业务区域及其交互合同。
- 状态模块负责明确生命周期和共享范围的状态。
- API/数据访问层负责传输合同，不承载页面提示和视觉状态。
- 纯函数负责解析、格式化、校验和确定性转换。
- 基础设施层负责请求、日志、监控、配置和跨业务能力。

不得建立职责不明的巨型 `utils`、`common` 或 `types/index` 作为默认归宿。

### 4.2 模块依赖

- 依赖方向应稳定、可解释，避免页面之间互相导入内部实现。
- 跨领域共享前先确认概念、合同和所有权确实稳定。
- 公共层不得反向依赖具体页面或偷渡某个业务规则。
- 循环依赖、隐藏全局可变状态和跨模块副作用必须消除或显式隔离。

## 5. 组件、复用与抽象

组件或模块的拆分依据是职责、状态所有权、生命周期、复用和测试边界，而不是固定行数。

适合拆分的信号包括：

- 存在独立的数据或请求生命周期；
- 存在独立交互、清理或状态同步；
- 已有多个真实调用方；
- 是稳定、可命名的业务区域；
- 修改局部需要理解大量无关代码；
- 可以形成更清晰的测试或样式边界。

不应仅因文件超过某个行数、两个区块外观相似或“未来可能复用”而抽象。50、200、500、1500 行等数字只能作为评审触发信号，不能作为自动拆分、合并或拒收标准。

共享能力按“页面局部 → 业务域内共享 → 多域共享 → 基础设施/设计系统”逐级提升。每次上移必须说明真实调用方、稳定合同、状态所有者和不负责的内容。

## 6. 命名、类型与数据模型

- 命名应表达业务意义和职责，遵循项目既有语言与风格。
- 布尔值使用可肯定理解的名称；避免双重否定。
- 类型应靠近其所有者：组件私有类型就近放置，领域类型归属领域模块，真正跨域且稳定的类型进入共享层。
- 禁止用 `any`、无约束字典或强制断言掩盖未知合同。未知输入应验证、收窄或在边界处解析。
- 请求参数、响应、事件、公共组件 API 和持久化数据必须有明确合同。
- 后端可能扩展的开放枚举不得被前端误建模为封闭集合；未知值应有可观察、可恢复的处理。
- 兼容别名、临时字段和默认值必须有来源、作用范围和删除条件，不建立永久猜测层。

## 7. API、错误与数据状态

### 7.1 合同优先

不得为了让页面先显示而猜测字段、响应包裹、分页字段、错误码、权限语义、上传字段或下载类型。合同不足时，应明确记录：已确认、文档滞后但已确认、前端提案、授权临时值、未知或不兼容。

### 7.2 分层责任

错误处理必须由项目技术基线定义责任矩阵，而不是固定为“全部由拦截器弹”或“全部由页面处理”。推荐边界：

| 层级 | 典型责任 |
| --- | --- |
| 传输层 | 认证附加、超时、网络/协议解析、统一响应解包、可识别的全局失效 |
| API/领域层 | 请求与响应类型、必要适配、领域错误分类 |
| 页面/交互层 | loading、empty、error、permission、重试、用户操作反馈和局部恢复 |

同一个失败不得由多个层级重复提示。全局提示不能替代页面内可恢复状态，页面提示也不能吞掉需要全局处理的认证或基础设施故障。

### 7.3 状态诚实性

必须区分：加载中、成功非空、成功为空、失败、无权限、未接入、离线/降级、显式开发 Mock 和未知合同。不得把失败转换成空数组并声称成功，也不得用漂亮 Mock 覆盖真实空数据或异常。

## 8. 状态、异步与副作用

- 状态放在能解释其创建、重置、共享和销毁规则的最近所有者处。
- 派生值优先计算，不重复存储可推导状态。
- `watch`、订阅或效果只用于真实副作用，不用来修补失控的数据流。
- 快速筛选、翻页、切换或自动刷新存在并发时，应防止旧响应覆盖新状态；单次请求不要过度设计取消框架。
- 定时器、事件监听、观察器、图表实例、WebSocket/SSE、Worker、媒体流、AbortController 和 Blob URL 必须在所有权结束时清理。
- 表单提交、批量操作和高代价请求应防重复；幂等不能仅依赖按钮禁用，后端仍应按业务风险保证。
- 缓存只在有明确收益时引入，并定义键、成功/失败语义、TTL、失效和容量。

## 9. 路由、权限与安全边界

- 路由路径、参数、查询、导航来源、刷新恢复和返回行为应形成可验证合同。
- 前端权限控制只改善可见性和交互，不能替代后端授权和数据范围校验。
- 前端是否使用 `canXxx`、权限码、角色或能力对象，取决于已确认接口合同，不设通用固定字段。
- 隐藏按钮不等于安全；所有敏感读写、导出、上传和下载必须由服务端校验完整范围。
- `v-html`、URL、文件、富文本和跨窗口消息必须验证来源并按风险清洗、限制或隔离。
- 不在前端代码、构建产物、日志和文档中写入密钥、Token、Cookie 或生产凭据。

## 10. UI、样式与响应式

### 10.1 设计系统与样式所有权

- 现有产品优先复用现有设计系统、token、组件和交互语言；未经授权不重做视觉方向。
- 新项目应建立最小 token 层，至少明确颜色、字体、间距、圆角、阴影、层级和断点的来源。
- 区分 token/theme、reset/base、layout/shell、utility、component 和有理由的 override。
- 页面私有问题保持局部；不得用全局选择器解决单页缺陷。
- 不用不断增加 `!important` 代替 DOM、作用域、优先级和所有权诊断。

### 10.2 状态与内容韧性

交互组件按实际范围覆盖 hover、focus、active、disabled、loading、empty、error 和 success。布局必须考虑长文本、空值、大数字、国际化、缩放、窄屏和动态数据量，不依赖样例内容恰好合适。

### 10.3 响应式

响应式策略由产品目标和项目基线确定，可以是流式重排、断点布局、固定逻辑画布或受控缩放。不得因为设计稿是某个尺寸就假设运行环境固定，也不得把内部切图尺寸当作业务容器尺寸。

## 11. 可访问性与可用性

- 使用语义 HTML、正确的标题层级、地标、标签和表单关系。
- 所有可操作元素应能通过键盘到达并有可见焦点；不要用无语义容器模拟按钮而不补齐行为。
- 状态和错误不能只依赖颜色表达；文本、图标或语义属性应提供等价信息。
- 文本和关键控件应满足项目采用的对比度与触控尺寸标准。
- 动效应尊重 `prefers-reduced-motion`，并允许用户暂停影响阅读或操作的自动行为。
- 弹窗、抽屉、菜单和提示需正确管理焦点、关闭方式和屏幕阅读器语义。

## 12. 表单、表格、文件与可视化

### 12.1 表单

- 区分展示模型与提交模型，提交前显式完成单位、空值、日期和字段转换。
- 客户端校验服务于即时反馈，不能替代服务端业务校验。
- 编辑初始化、重置、取消、离开未保存提示和提交恢复必须有一致语义。
- 错误应定位到可操作位置；提交失败后不得丢失用户输入。

### 12.2 表格与大数据量

- 分页、排序、筛选和选择状态必须与接口合同一致。
- 空结果、请求失败和无权限不能渲染成同一种空表格。
- 大数据量采用分页、虚拟化或渐进加载前，先确认交互、可访问性和服务端能力。

### 12.3 上传、下载与预览

- 核对字段名、MIME、大小、文件名、授权、进度、取消和错误合同。
- Blob 与 URL 两种下载合同不得混用；对象 URL 使用后必须释放。
- 预览失败应保留可理解状态和安全的下载退路，但不得绕过授权。

### 12.4 图表和动态媒体

- 图表容器、实例、resize、隐藏后恢复和销毁必须有明确生命周期。
- 颜色、图例、坐标、提示、空态和业务口径按图表逐项确认，不用通用主题掩盖差异。
- 构建成功不能证明图表已经渲染、尺寸正确或交互有效。

## 13. 性能与依赖

- 先测量瓶颈，再选择优化；不为了“性能”提前引入复杂缓存、分包或状态系统。
- 关注网络、包体、解析执行、渲染、列表规模、图片字体和第三方脚本，而不只关注动画。
- 路由和大模块是否懒加载、依赖是否按需加载，由真实体积和访问路径决定。
- 新依赖必须说明必要性、维护状态、许可证、安全、体积、浏览器/框架兼容和替代方案。
- 锁文件必须与包管理器一致；不得通过关闭 TLS、忽略完整性或吞掉安装错误来“修复”依赖问题。

## 14. 注释与文档

注释用于说明代码不能直接表达的职责、来源、生命周期、单位、关键转换、兼容原因和非显然决策。

应该注释：主要业务区域、重要 API/业务方法、复杂状态同步、竞态保护、清理、特殊布局、派生样式和图表业务编码。

不应注释：显而易见的变量、逐行语法、聊天残留、历史抱怨、未确认推测和“特殊处理”“防止报错”等空话。

AI 来源不写入每个方法或模板节点。AI 参与通过 Git trailer、PR 和变更记录追溯；代码注释只解释当前代码。

## 15. 验证与质量门禁

项目必须声明真实可执行的格式、lint、类型、测试、构建和运行命令。脚本存在但依赖缺失、CI 使用另一套命令或错误被吞掉，均不能称为质量门禁已建立。

验证按风险选择并分层报告：

1. **差异/源码**：范围、编码、导入、链接和合同检查；
2. **静态**：格式、lint、类型、编译、配置和依赖解析；
3. **测试**：相关单元、组件、集成或端到端行为；
4. **运行**：目标路由、真实 DOM、控制台、请求和资源清理；
5. **视觉/交互**：目标视口、状态、焦点、滚动、弹层和截图；
6. **外部**：真实后端、设备、部署、第三方服务或人工验收。

低层通过不能推出高层通过。未执行的检查必须写“未完成”或“不适用”，并说明边界。

## 16. 评审最小清单

```text
[ ] 需求、验收、不做范围和授权边界清楚
[ ] 工作区已有修改受到保护
[ ] 改动与项目架构、命名和既有合同一致
[ ] 未猜测接口、权限、设计值或运行结果
[ ] 类型、状态、错误和 Mock 边界清楚
[ ] 组件与公共抽象有真实责任和所有者
[ ] 权限由后端最终校验，敏感数据没有泄露
[ ] loading/empty/error/permission 等状态可区分
[ ] 副作用和资源已清理
[ ] 可访问性、响应式和内容边界已按范围检查
[ ] 新依赖和公共合同有必要性与验证
[ ] 注释解释职责和原因，没有机械叙述
[ ] 实际执行的验证及未验证项已分别记录
[ ] diff 不含无关格式化、调试代码、秘密或临时产物
```
