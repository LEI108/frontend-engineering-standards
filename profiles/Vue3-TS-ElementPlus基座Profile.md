# Vue 3 + TypeScript + Element Plus 基座 Profile

> 版本：1.0.0  
> 性质：技术栈专项正式规范  
> 前置：必须同时遵守 `standards/前端工程开发规范（通用版）.md`

本 Profile 为以 Vue 3、TypeScript、Element Plus 为主的管理端和业务应用提供稳定工程基线。它规定长期成立的栈内原则，不固定某个项目的精确版本、路由模式、接口字段、主题色或本地工具封装。

## 1. 项目基线先行

项目开始开发前，必须基于 `项目技术基线配置模板.md` 明确并版本化记录：

- Vue、TypeScript、Vite、Element Plus、Vue Router、状态库、请求库和包管理器版本；
- Node 版本和 lockfile 策略；
- SFC 风格、目录组织、路径别名和代码格式；
- 路由模式、部署 base、权限合同和页面缓存策略；
- API 响应包裹、分页字段、错误责任和文件传输合同；
- Element Plus 引入方式、图标策略、语言包和主题机制；
- lint、类型、测试、构建、运行和视觉验证命令。

通用 Profile 不替项目选择 hash/history 路由、全量/按需组件注册、分页字段 `list/rows/records`、精确依赖版本或错误提示工具。

## 2. TypeScript 基线

- 新项目必须启用 `strict`，不得通过关闭严格模式解决类型错误。
- `moduleResolution`、target、路径别名和 Vue 类型检查器版本必须与实际 Vite/TS 组合兼容。
- API 参数、响应、组件 props/emits、表单提交和公共函数必须有明确类型。
- 类型按所有权组织：组件私有类型就近、领域类型放在领域模块、稳定跨域类型进入共享目录。
- 共享 `types/index.ts` 可以作为受控导出入口，但不得成为所有业务类型的单一巨型实现文件。
- 类型导入使用 `import type`；运行时常量使用普通 import。
- `unknown` 在边界处收窄；谨慎使用非空断言和类型断言，并让控制流先证明安全条件。
- 后端开放枚举优先保留可扩展性；封闭联合只用于合同明确且前端必须穷举的集合。

项目应独立运行 `vue-tsc --noEmit` 或等价检查；`vite build` 不能替代完整类型检查。

## 3. 单文件组件

### 3.1 默认写法

新组件默认采用：

```vue
<script setup lang="ts">
</script>

<template>
</template>

<style scoped>
</style>
```

既有项目应保持已建立的块顺序、样式语言和 Composition/Options API 风格。迁移旧组件必须作为明确任务，不能在普通功能改动中顺带完成。

### 3.2 Props、Emits 与 v-model

- 使用类型化 `defineProps`、`defineEmits`；只有可选项才提供默认值。
- props 视为只读。需要编辑时建立清晰的本地草稿并定义与父级的同步时机。
- 组件事件表达已发生的领域或交互事实，避免泄漏内部 DOM 细节。
- `v-model` 使用项目确认的 Vue 3 合同；多个 model 必须有清晰语义。
- 公共组件应记录 props、事件、插槽、状态所有权、受控/非受控行为和错误状态。

### 3.3 组件边界

页面负责组合，业务组件负责稳定区域，composable 负责可复用状态与副作用，纯函数负责确定性转换。不要按模板中的每个视觉矩形拆组件，也不要把有 UI 的能力藏入 composable。

组件拆分依据职责和生命周期。文件体量只用于触发评审，不作为机械拆分线。

## 4. 响应式状态与 Composition API

- 用 `ref` 表达可替换值，用 `reactive` 表达稳定对象；不要为了风格统一强行只用一种。
- 计算值使用 `computed`，避免用 `watch` 同步可直接推导的数据。
- `watch`/`watchEffect` 必须说明真实副作用、触发源、立即执行和清理语义。
- 解构响应式对象时使用项目认可的安全方式，避免静默丢失响应性。
- 生命周期注册放在可发现的位置；同一资源的创建和清理应靠近。
- 异步操作应在写回前核对当前筛选、路由或请求版本，防止过期响应覆盖新状态。
- `<KeepAlive>` 页面明确 `onMounted`、`onActivated`、缓存状态和刷新策略；表单草稿不能因通用刷新逻辑被意外覆盖。

## 5. 状态管理

- 页面私有状态保留在页面或领域组件；只有跨页面共享、跨生命周期保留或需集中协调的状态进入 Pinia/状态库。
- Store 按业务域和所有权拆分，不按“所有请求”“所有弹窗”建立巨型 Store。
- Store 可以协调领域动作，但默认不直接弹 UI 消息；交互反馈由调用页面负责，除非项目基线定义了统一通知领域。
- Store 的持久化字段、用户/租户切换清理、登出清理和并发请求必须明确。
- 不把服务端数据无差别永久缓存；缓存需要键、TTL、失效、失败和容量合同。

## 6. 路由与页面生命周期

- 路由使用 Vue Router 4 的项目既有模式；hash/history、base 和服务端回退写入项目基线。
- 路由名称、路径、params/query、meta 字段和页面标题应有稳定语义和类型支持。
- 改路由前追踪菜单、导航调用方、外链、刷新恢复和部署路径。
- 路由守卫负责导航级流程，不承担后端授权；页面可见性也不是安全边界。
- 路由级懒加载按访问路径和包体决定，不机械为每个小组件创建异步边界。
- Teleport 弹层、未完成请求、监听器和页面缓存需要在离开/卸载时按所有权处理。

## 7. API 与错误责任

### 7.1 API 模块

API 模块按业务域组织，负责方法、URL、`params/data/FormData`、响应类型和必要传输选项。不要按 HTTP 动词拆文件，也不要把所有接口堆入单一入口。

页面/领域层负责查询状态、展示转换、loading、empty、error、permission、重试和局部通知。仅在多个调用方需要相同且稳定的转换时建立适配器。

### 7.2 错误矩阵

项目必须填写类似下表的实际合同：

| 错误类别 | 请求层 | API/领域层 | 页面层 |
| --- | --- | --- | --- |
| 网络/超时 | 标准化错误 | 可选分类 | 展示可重试状态 |
| 登录失效 | 统一协调一次 | 透传 | 避免重复提示 |
| 业务校验 | 解包并保留服务端信息 | 可映射字段 | 定位表单或操作反馈 |
| 局部加载失败 | 不伪装空数据 | 保留语义 | 局部错误与重试 |

不得写成“所有错误拦截器统一弹，页面不要处理”。同一错误只能由一个所有者负责 toast，但页面仍需收敛 loading、旧数据和重试状态。

### 7.3 响应和分页

响应包裹、成功码、分页字段和空值语义以项目合同为准。禁止在通用工具中猜测 `data/list/rows/records` 多套别名来掩盖合同不清。

## 8. 权限

- 后端是鉴权、授权和数据范围的最终权威。
- 前端根据确认合同渲染可见性和可操作性；可以使用权限码、能力对象或 `canXxx`，但 Profile 不强制某一种字段。
- 任何提交的资源 ID、组织 ID 和批量范围都必须由后端重新校验。
- 页面不应根据显示标签或角色名称自行推导敏感权限。
- 无权限、功能关闭、数据为空和接口失败必须能区分。

## 9. Element Plus 使用

### 9.1 引入和组件 API

- 全量或按需引入、自动导入、图标注册和语言包由包体、项目工具链和现状决定并写入基线。
- 优先使用 Element Plus 的公开 API、CSS 变量和插槽；不依赖未记录的内部 DOM，确需覆盖时锁定版本并进行运行验证。
- 同一领域保持一致的表单、弹窗、表格、分页和通知封装，不同时维护多套语义相同 API。

### 9.2 弹层、Teleport 与样式

- Dialog、Drawer、Dropdown、Select、Tooltip 等可能 Teleport 到 body。scoped 样式是否命中必须通过真实 DOM 和编译选择器确认。
- 弹层定义焦点进入/返回、ESC、遮罩关闭、滚动锁定、加载、提交防重和移动端行为。
- 不直接累积全局覆盖或 `!important`；先确认 `popper-class`、命名空间、CSS 变量、`:deep()` 和 Teleport 目标。
- 深度选择器使用当前 Vue 工具链支持的语法，以编译结果为准，不把某一历史写法当永恒规则。

### 9.3 表单

- 使用 `FormInstance` 等公开类型，不以 `any` 绕过校验。
- 校验、提交防重、服务端字段错误、关闭/重置和编辑初始化有一致流程。
- 日期、数字、空字符串、数组和 ID 在提交边界显式转换。
- 动态表单项使用稳定 key，删除项同步清理校验状态。

### 9.4 表格

- 列定义、行主键、选择状态、分页和服务端排序保持一致。
- 操作权限来自确认合同；操作列不硬编码角色推断。
- 大表格先确认数据量和交互，再选择虚拟表格、服务端分页或局部渲染。
- 表格在窄屏的策略可以是滚动、列优先级、卡片化或专门移动页面，由产品和数据密度决定，不强制单一路径。

## 10. 样式与主题

- 建立项目 token，并优先通过 Element Plus CSS 变量对齐主题；修改主色时检查其派生变量，但不强制某组固定色值。
- 组件局部样式放在所有者附近，全局层只承载 token、基础、布局、稳定 utility 和有记录的全局覆盖。
- CSS 类名表达业务或组件语义，避免依赖生成 DOM 顺序和脆弱的 `nth-child`。
- 组件库样式问题必须检查实际 DOM、scoped 属性、Teleport、优先级和 `getComputedStyle`。
- 响应式断点、容器查询或固定画布策略由项目基线声明；页面不能私自创建冲突的第二套断点系统。

## 11. 可访问性

- 表单 label、帮助、错误和控件建立程序化关联。
- 图标按钮提供可访问名称；只读图标不进入无意义 Tab 顺序。
- Dialog/Drawer 使用组件库焦点管理并验证实际行为；自定义弹层必须满足同等语义。
- 表格、分页、菜单、Tabs 和 Tree 保留键盘操作，不因视觉定制破坏角色与焦点。
- 状态标签不只靠颜色；动效和自动轮播尊重 reduced motion。

## 12. 性能与资源

- 避免全量响应式包装大型不可变配置，可按需使用 `shallowRef`、`markRaw` 或普通常量，但要说明所有权。
- 图表、编辑器、预览器等重依赖按真实访问路径加载；检查打包产物后再决定分包。
- `ResizeObserver`、窗口监听和图表 resize 应只有一个清晰所有者并进行合并调度。
- 图片、字体、图标和本地化包按产品需求选择格式、尺寸和加载策略。
- 不因“Vue 最佳实践”无证据地加入 VueUse、自动导入、第二状态库或新的请求层。

## 13. 测试与验证

最低检查由改动风险决定：

- 类型/API/路由：`vue-tsc`、相关测试和路由检查；
- 组件交互：组件或浏览器测试，覆盖 props/events/loading/empty/error；
- Element Plus 样式：真实 DOM、编译选择器、winning rule 和 computed style；
- 页面行为：目标路由、实际请求、控制台和卸载清理；
- UI：约定视口、长内容、窄屏、键盘和弹层；
- 构建/依赖变更：干净安装条件、构建产物和部署 base。

构建通过不能代替类型、运行或视觉验收。检查结果必须记录执行命令和边界。

## 14. 明确不采用的旧式硬规则

本 Profile 不采用以下规则：

- 所有类型集中在单一 `types/index.ts`；
- 所有错误只由全局拦截器弹出；
- 页面只能渲染固定命名的 `canXxx` 字段；
- 固定使用 hash 路由；
- 全量全局注册所有 Element Plus 组件或图标；
- 固定使用某组依赖版本、颜色、断点、分页字段和本地 helper；
- 以 50/200/500/1500 行作为机械拆分或合入条件；
- 逐方法添加 AI 来源注释；
- 因组件库已安装就默认它的视觉和交互一定符合需求。

这些内容如在某项目成立，应作为经过验证的项目技术基线，而不是 Vue 3 通则。
